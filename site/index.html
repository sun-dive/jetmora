jetmora A bundle of threads of signed script ticks, existing outside any blockchain.

A program runs. It produces a result. Somebody else, somewhere else, later, possibly much later, needs to know that result is what the program actually produces.

Today they have two options. Trust whoever ran it. Or run it again, and hope they can find the same program, the same inputs, and an interpreter that behaves identically.

jetmora makes the second option cheap and exact, and keeps it possible for as long as anyone keeps the thread. Each step of a program is a tick in a thread: signed by its owner, judged by the thread's own script, and kept with everything needed to run it again.

That last part is doing more work than it looks. Keeping a result is easy. Keeping the ability to check it is the hard half, and it is the half that quietly gets lost. A record you can no longer execute is only half preserved.

Verification by re-execution, not by proof. This matters, because “verifiable computation” usually means zero-knowledge proofs: verify the answer without re-running the work. That is a fine thing and it is not this.

A zero-knowledge proof tells you the computation was performed correctly. It does not show you the work: the inputs and the steps stay hidden. For a clinical analysis, a safety calculation or a compliance check, seeing the work is the requirement.

Threads, ticks and tips

threadOne program's signed history: a beginning, then every tick since.
scriptThe small program inside a thread that decides which ticks are allowed.
tickOne step. Signed by the thread's owner, it spends the tip and makes the next one, and the thread's script decides whether it is allowed.
tipThe output of the thread's last tick. Only the tip can be ticked forward, by spending its output.
hostA server that keeps threads and checks each tick. Anyone can run one.
ropeThreads bundled together, as a host carries them. They never touch.
anchorA hash written to a blockchain when a timestamp matters.

Only the tip can be ticked forward, by spending its output. Once spent, there is no output to spend, and a second attempt is rejected, as Bitcoin rejects a spend of an output already spent. It is not a decision anyone makes: it is the state of the thread, because a spendable output only exists at the tip. At its host, a thread cannot fork.

A thread has one writer. Nobody else can tick it forward, so there is nothing to race.

The rules travel with the thread. They are in the tip's script, which checks each tick and, as jetForth BASIC writes it, passes itself on to the next tip. Nothing outside the thread decides what it may do: not the host, not the page that wrote the tick.

A computation, in one line

H(program) · H(input state) · engine revision
    →  H(output state)

H means a hash: a short fingerprint of the data. The engine revision is the exact version of the interpreter that ran it. Comparison is a single equality check, no matter how much work was done. A verifier never has to send you a result: it publishes a hash, and agreement is one line. Disagreement is just as cheap, and considerably more interesting: it names the exact computation to go and look at.

How a tick is judged

The same way a BSV node checks a payment. A tick carries data only, never instructions of its own. The thread's script then runs on that data, and the tick is accepted only if the script ends with a single answer that is not zero. Anything else refuses it. A host runs the script, and does not record a tick it refuses.

The limits belong to the engine revision, and they are the same on every host, because a limit that differed between hosts would be a verdict that differed between them:

instructions500,000 a tick; moving data costs one more for every 64 bytes
memory64 KB for the script, and 64 KB more for each function call while it runs; a further 64 KB for the tick's data, which the script can read but not change
stack1,000 values held at once
signatures100 checks a tick, a multi-signature check counting one for each key
sizea script of at most 500,000 bytes, and calls at most 64 deep

On a shared blockchain, a script that exhausts memory is every node's problem. That is why several instructions were switched off in Bitcoin in 2010, and they have been contentious ever since. Here every tick is bounded by its engine, and a bad tick is refused without touching any other thread.

A bad actor only gets to shoot themselves in the foot while everyone else carries on.

Written in jetForth BASIC, run as jetForth

Programs are written in jetForth BASIC and compiled once. A decompiler, the reader, turns the result back into BASIC, so the rules a thread runs can be read by a person, not only by a machine. Try it in your browser.

What runs is jetForth: a small language based on Forth, a compact programming language from 1970. Unlike Bitcoin's script it can loop, and it works in 64-bit numbers. Each tick names the engine that judges it, and a jetForth BASIC program says which on its first line, VERSION JF 3, so a verifier years from now runs the revision the tick named rather than its own.

Once a revision is fixed it never changes: a change is a new revision number. Revision 3 is not fixed yet. The engine runs in PHP and in JavaScript.

A tick will be able to name other engines too. One is Bitcoin's script as it stood in 2009, with the original instruction numbers; that engine runs scripts today but does not yet judge ticks. Bitcoin switched concatenate, multiply, substring and shift off in the middle of 2010, so an early program that used them cannot run there. BSV switched them back on, but gave three of the old numbers to different instructions, so some early programs run there and give a different answer. Named this way, a 2009 program runs as it was written. Nobody has yet looked for an early program that used them.

Who checks

The writer runs the script before signing a tick. The host runs it before recording one. And anyone can run it again.

Threads only need to agree when two parties don't trust each other. Then each has its own reason to mirror the other's thread and check that it didn't cheat, and cheating leaves proof: a party that signs two different versions of the same moment has signed the evidence against itself. The checking is done by the people with something at stake, not by a global queue. Mirroring catches cheating rather than queueing to prevent it. The licence lets anyone run a host, a witness or a mirror.

A thread belongs to the key that signs it, and its owner holds it and can back it up however they choose. A user's thread a host carries and checks, but cannot tick: that takes the user's key. Of a user's thread, a host is a witness, not a custodian.

Some threads are the host's own. Comments, likes and views live on threads of their own, signed by the host, so audience numbers can be proved rather than just quoted, and they never mix with the thread they are about. Each comment and like is signed by the person who made it as well: the host decides what appears, but cannot decide who said it. A thread holds the actions; the totals are counts kept beside it, and can always be recounted from it.

What a dishonest host could do is show one history to some people and another to others. That leaves evidence it cannot take back: the host signs a summary of everything it holds, and two signed summaries that disagree are proof anyone can show.

Anchors

A thread needs no blockchain. When a timestamp matters, a hash is anchored on one: the host's summary, which covers every thread it holds, or a single thread's tip. Thirty-two bytes, on whichever blockchain you choose, and the thread stays where it is. An anchor proves the thread existed by then; only running it again shows its ticks were valid. And once a tip is anchored, nothing before it can be quietly rewritten, which is why one writer per thread is enough.

What is left for a blockchain is the one thing it is uniquely good at: a public clock that nobody can wind back. Use the blockchain as a clock, not as a ledger.

You can always pull up an anchor; you are not chained to anything. A chain binds. An anchor holds only while you choose.

There is no coin, no consensus, and no global ordering. A blockchain sends every transaction to every node, so its cost grows with the network. A thread only goes to whoever is watching. Every thread keeps its own order, and no host waits on another, so capacity grows by adding hosts, with no coordination at all.

latencyA tick is a step, not an agreement: it waits on its own host and nothing else.
parallelismNo global sequence to serialise into: hosts never wait on each other.
costNo protocol fee, because nothing shared is being rationed.

Blockchains often advertise throughput: how many transactions a second. Physics needs latency, and no amount of throughput buys back a round trip you did not take.

Why no fee

Programs that hold value and enforce their own rules, covenants, are a good way to build things. They do not ask permission, they do not care who you are, and you cannot talk them out of their rules.

On a public blockchain they have one structural weakness, and it is not in the program. A covenant must pay a fee to move, and one that writes a fee bound into itself can be stranded when the network's minimum rises above it: stuck, with whatever it holds. One of our own covenants on BSV has about one percent of headroom: let the fee floor rise further and it can no longer move.

The flaw is not the number. It is that one side of the arrangement is bound forever and the other is not bound at all, and the unbound side sets the value.

And a fee on every step is its own harm: nickel and diming users with a micropayment on every pointless transaction, a turnstile on every action, for ever. Every payment is a moment where someone decides whether the action was worth it, and that is where use dies. The web won because reading a page costs nothing at the moment you read it.

A jetmora script never references a fee, and nobody is charged for every action. A host may charge for its service, and nothing that cannot change depends on that price. And because a thread belongs to its owner, it is designed to move: a host that overcharges would watch its threads leave. Exit is what disciplines the price.

What it is for

Underneath the applications there are only two building blocks: a witnessed claim, and a witnessed computation on it. Everything below is those two, pointed somewhere different.

scienceReproducibility is not “here is my repository.” It is here is the execution: same program, same inputs, same intermediate states, or a provable divergence.
medicineA trial's analysis plan, committed and timestamped before the data arrives. Then the data arrives and it runs. Provably not adjusted afterwards.
standardsA safety standard is a computation. Published as a program, a manufacturer proves compliance by running it, and a regulator verifies without trusting anyone's spreadsheet.
engineeringA load rating becomes a program, with the formula's revision pinned to a date.
oraclesAn oracle is a service that reports outside facts, such as prices, to a program. jetmora cannot make one honest. It makes one accountable: statements are signed, in order, and cannot be quietly revised. A track record becomes something you can compute.

Not new, and that is the point

Three of the eight references in Bitcoin's white paper are Haber and Stornetta's digital timestamping papers. Linked records, witnessed, tamper-evident, and no coin anywhere. Their company published a hash every week in an advertisement in the New York Times, which is an anchor done in newsprint.

The coin was never the point of the record. It was the payment for the consensus. Remove the need for open permissionless agreement and the coin has no job left to do.

And jetmora has no coin. There is nothing to buy or hold, and no exchange to open an account with. Its value can't come from a coin, so it only comes from what it is used for: the use case is the value. It's a protocol, much like TCP: it sits underneath, out of sight, and the people using it never think about it.

Coinless systems did not stop working; they stopped being called blockchains. Certificate Transparency secures the certificate ecosystem of the entire web, and blockchain projects barely mention it. Git, which most programmers use every day, is built the same way.

The record-keeping here is a thirty-five-year-old tradition. What jetmora adds to it is a program inside each record, which anyone can run again, still with no coin.

Status

Early, and public while it is still moving.

The engine in both languages, the compiler and its reader, and their tests are published. The two interpreters are graded against each other on every test case, refusals included, because agreement on a failure is still agreement: it is what tells you a disagreement is in your test rather than in the implementations.
